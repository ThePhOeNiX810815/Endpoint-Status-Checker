## 2 — Bug Fix: Issue #36 — SendARP Causes Machine Restart

### Root cause
`NativeMethods.SendARP` is not thread-safe. When the parallel scan loop called it
simultaneously from many threads, concurrent ARP requests could trigger a NIC
driver fault that caused a BSOD/restart on some machines.

### Fix — `src/ArpLookup/WindowsLookupService.cs`
A `SemaphoreSlim(1, 1)` serialises all `SendARP` P/Invoke calls:

```csharp
private static readonly SemaphoreSlim _arpThrottle = new SemaphoreSlim(1, 1);

public static string Lookup(IPAddress ip)
{
    _arpThrottle.Wait();
    try {
        // … SendARP call …
    } finally { _arpThrottle.Release(); }
}
```

## 3 — Bug Fix: Issue #35 — Special Characters in URLs Break Parsing

### Root cause 1 — pipe `|` in endpoint name
The endpoint list line format is `Name|URL`. The original `Split('|')` call without
a count limit would split again on a `|` that appeared inside the URL itself.

### Fix — `src/CheckerMainForm.cs` (~line 4024)
```csharp
string[] lineParts = line.Split(new char[] { '|' }, 2);   // max 2 parts
string lineAddress = lineParts.Length > 1 ? lineParts[1].Trim() : lineParts[0].Trim();
string lineName    = lineParts[0].Trim();
```

### Root cause 2 — unescaped characters in URL
URLs with spaces, brackets, or other RFC-3986 special characters would fail
`Uri.IsWellFormedUriString` validation, causing the endpoint to be skipped.

### Fix — `src/CheckerMainForm.cs` (~line 4125)
```csharp
if (!Uri.IsWellFormedUriString(address, UriKind.Absolute))
{
    string escaped = Uri.EscapeUriString(address);
    if (Uri.IsWellFormedUriString(escaped, UriKind.Absolute))
    {
        endpointStatusDefiniton.Address = escaped;
        endpointStatusDefiniton.ResponseAddress = escaped;
    }
}
```

## 5 — Bug Fix: Issue #32 — Cloudflare 403 Detection

### Root cause
Endpoints behind Cloudflare return HTTP 403/429/503 with a browser challenge
page. The app reported these as `"Forbidden"` or `"Service Unavailable"`, giving
no indication the endpoint is actually reachable but protected.

### Changes — `src/CheckerMainForm.cs`

**Helper method (added near `GetHTTPWebHeaders`):**
```csharp
private static bool IsCloudflareProtected(HttpWebResponse response)
{
    if (response == null) return false;
    bool hasCfRay    = !string.IsNullOrEmpty(response.Headers["CF-RAY"]);
    bool hasCfServer = response.Server?.IndexOf("cloudflare",
                           StringComparison.OrdinalIgnoreCase) >= 0;
    return hasCfRay || hasCfServer;
}
```

Detection fingerprint: the `CF-RAY` response header is injected by Cloudflare's
edge on every proxied response — including challenge pages — so its presence is a
reliable indicator even when the HTTP status alone could be ambiguous.

**Scan loop annotation (WebException handler):**
```csharp
if (IsCloudflareProtected(httpWebResponse))
{
    string cfRay = httpWebResponse.Headers["CF-RAY"];
    endpoint.ResponseMessage +=
        " [Cloudflare Bot Protection" +
        (!string.IsNullOrEmpty(cfRay) ? " | CF-RAY: " + cfRay : string.Empty) +
        "]";
    // → bypass logic follows (see §6)
}
```

**HTTP headers improved (in `PrepareHTTPWebRequest`):**
- `Accept` set to the full Chrome-style accept string (includes `image/avif,image/webp`)
- `Sec-Fetch-Mode` corrected from `"Sec-Fetch-Node"` (typo, invalid) → `"navigate"`
- `Sec-Fetch-Site` corrected from `"same-origin"` → `"none"` (correct for direct navigation)
- `Sec-Fetch-Dest` corrected from `"empty"` → `"document"`
- `Sec-Fetch-User` set to `"?1"` (missing entirely before)

## 6 — New Feature: Three-Mode Cloudflare Bypass

### What was added

When `IsCloudflareProtected()` returns true, the scan loop now attempts a bypass
using the method selected in **Settings → CF BYPASS** (new main-menu item).

Three modes are available:

| Mode | Description |
|---|---|
| **Disabled** (default) | No bypass — status shown as `[Cloudflare Bot Protection \| CF-RAY: …]` |
| **Playwright** | Launches a headless Chromium instance (~120 MB one-time download) that mimics a real browser, bypassing both JS challenges and JA3/JA4 TLS fingerprint checks |
| **FlareSolverr** | Posts to an external FlareSolverr JSON API (default: `http://localhost:8191/v1`) — a standalone Python + undetected-chromedriver proxy that handles challenges externally |

### Why JA3/JA4 fingerprinting matters
`HttpWebRequest` sends a TLS `ClientHello` with a fixed cipher-suite list that
Cloudflare's edge recognises as a non-browser fingerprint. Header spoofing alone
cannot fix this — only a real Chromium browser (Playwright or FlareSolverr) sends
the correct JA4 fingerprint.

### New files
| File | Purpose |
|---|---|
| `src/CloudflareBypassChecker.cs` | `CloudflareBypassMethod` enum, `CloudflareBypassResult` DTO, `CloudflareBypassChecker` static class (Playwright + FlareSolverr logic) |
| `src/CloudflareBypassSettingsDialog.cs` | WinForms dialog — code-behind |
| `src/CloudflareBypassSettingsDialog.Designer.cs` | WinForms dialog — layout |

### New settings
| Setting | Type | Default | Purpose |
|---|---|---|---|
| `Config_CloudflareBypass_Method` | `int` | `0` (Disabled) | Selected bypass mode |
| `Config_FlareSolverr_URL` | `string` | `http://localhost:8191` | FlareSolverr base URL |

Both settings are persisted in `Properties/Settings.settings` + `app.config` and
saved via `Settings.Default.Save()` when the user clicks OK in the CF Bypass dialog.

### Playwright concurrency guard
A `SemaphoreSlim(2, 2)` limits simultaneous headless Chromium instances to 2,
preventing RAM exhaustion when many CF-protected endpoints are scanned in parallel.

### Playwright one-time install
`Microsoft.Playwright.Program.Main(new[] { "install", "chromium" })` is called
once on the first bypass attempt (double-checked lock, `volatile bool` flag).
The "Install / Update Chromium" button in the CF Bypass dialog also triggers it
manually.
