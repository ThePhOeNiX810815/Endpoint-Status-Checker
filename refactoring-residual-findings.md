# Endpoint Status Checker v3 Residual Findings

This review covers v3 production code after Tickets 1-4 were merged. The current v3 integration branch is `Main-Dev-V3`.

The codebase is not fully untangled. The programme reduced several compatibility-sensitive boundaries, but large WinForms classes still contain protocol, persistence, export, and UI logic that should be changed only with stronger characterization.

| File and symbol | Remaining issue | Reason it was not changed | Severity | Recommended future action |
| --- | --- | --- | --- | --- |
| `src/CheckerMainForm.cs` / `CheckerMainForm` | The class remains very large and still coordinates UI, endpoint checks, HTTP/FTP/ping/DNS/MAC work, persistence, export, theming, and tray behavior. | Splitting the whole form safely requires broader UI and workflow characterization than is available in this environment. | High | Continue extracting cohesive boundaries one protocol or workflow at a time, keeping the form as orchestration. |
| `src/CheckerMainForm.cs` / `bw_GetStatus_DoWork` | The endpoint-check workflow still has deeply nested protocol, redirect, response, SSL, retry, DNS, MAC, ping, cancellation, and export orchestration logic. | HTTP status codes, Cloudflare handling, redirects, SSL handling, timeouts, and cancellation are compatibility-sensitive and need integration tests before deeper movement. | High | Add local fake HTTP/FTP/DNS-style characterization harnesses, then extract protocol handlers and result mappers in small PRs. |
| `src/CheckerMainForm.cs` / `EndpointsStatusExport` | XLSX and HTML export generation are still embedded in the form and use ClosedXML, Spire.Xls, file locking, progress UI, and `Application.DoEvents` in one method. | XLSX/HTML output shape, hidden columns, colors, file names, and lock behavior are compatibility-sensitive; extracting without golden-file tests risks regressions. | High | Add golden-file or workbook-structure tests, then extract XLSX generation and HTML post-processing separately. |
| `src/CheckerMainForm.cs` / comments throughout the form | Many comments repeat the following statement or compensate for method size, such as section labels inside large workflows. | Removing comments in bulk would create noisy churn and could discard useful compatibility hints mixed among redundant comments. | Medium | Remove redundant comments opportunistically when the surrounding method is extracted or reduced. |
| `src/EndpointDetailsDialog.cs` / `EndpointDetailsDialog` | Dialog still mixes UI presentation with favicon lookup, WMI, port checks, WHOIS, MAC vendor lookup, geolocation, VirusTotal, page-link validation, and process launching. | Each workflow has external I/O and user-visible behavior; safe extraction needs focused tests and potentially separate tickets. | High | Extract network/API clients and result mappers behind narrow internal boundaries, starting with pure formatting/mapping logic. |
| `src/SpeedTestDialog.cs` / `SpeedTestDialog` | Dialog remains large and combines UI state, speed-test orchestration, calculations, rendering, settings, and exception presentation. | Speed-test behavior depends on external servers and UI timing, which are not safely covered by existing tests. | Medium | Characterize calculation and formatting helpers first, then isolate speed-test orchestration from UI updates. |
| `src/Program.cs` / global static application state | Program owns mutable global configuration, file names, API keys, app metadata, and startup/update flow. | Several public/static members are effectively public compatibility surface and are used across forms. | Medium | Introduce read-only snapshots for new boundaries, but do not remove or rename public/static fields without an explicit compatibility decision. |
| `src/CloudflareBypassChecker.cs` / bypass methods | Cloudflare bypass logic mixes process management, FlareSolverr HTTP calls, Playwright/CDP websocket control, JSON parsing, and cleanup. | Behavior is protocol- and environment-sensitive; changing it risks breaking configured bypass workflows. | High | Add tests around result mapping and command construction, then split FlareSolverr and Playwright implementations. |
| `src/ExceptionDialog.cs` and `src/FeatureRequestDialog.cs` / mail composition and fallback save | Near-duplicated mail composition, `.eml` save, temp directory, and UI status handling exist in both dialogs. | Shared behavior appears similar but not proven identical; public/user-facing error reporting must be preserved. | Medium | Add tests for generated mail messages and fallback file behavior, then extract a mail-report composer only for identical behavior. |
| `src/CheckerMainForm.cs`, `src/EndpointDetailsDialog.cs`, `src/FeatureRequestDialog.cs`, `src/ExceptionDialog.cs` / `NewBackgroundThread` and `ThreadSafeInvoke` | Thread helper patterns are duplicated across forms and include `Application.DoEvents`. | `Application.DoEvents` can affect UI reentrancy and timing; deduplication may change behavior. | Medium | Characterize UI-thread invocation expectations before consolidating helpers. |
| `src/EndpointDetailsDialog.cs` / VirusTotal `.Result` usage | Async VirusTotal calls are synchronously blocked with `.Result` inside worker paths. | Altering async flow could change timing, retry, exception, and UI update behavior. | Medium | Add behavior tests or manual workflow coverage, then convert one workflow at a time if safe. |
| `src/ArpLookup/WindowsLookupService.cs` / `Lookup` | ARP lookup uses platform-specific command/PInvoke behavior and a static throttle. | It is compatibility-sensitive for MAC resolution and Windows networking behavior. | Medium | Keep isolated; add tests around formatting and failure mapping before any behavioral cleanup. |
| `src/IPAddressExtensions.cs` / namespace `Knom.Helpers.Net` | Namespace and helper naming do not match the application namespace. | Public extension methods may be referenced externally; renaming would be a public API change. | Low | Keep public namespace unless a compatibility-breaking cleanup is explicitly approved. |
